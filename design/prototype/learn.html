Reference

The rules behind the view.

Nothing in Binlet is magic: a record is a text line with a small arithmetic contract, and an address is either in the file or assumed by you. These six sections cover the difference.

01 · What a record actually is

One Intel HEX line is a complete, self-describing packet. Count tells you how many data bytes follow; address says where they load; type says what the line means; checksum closes the packet.

Intel HEX

The failing record, field by field

Count · 04Four data bytes follow. A line is not a row of hex; the count defines its shape.
Address · 8020Offset inside the current 64 KiB page. The type 04 record above supplies the upper bits.
Type · 0000 is data. 01 ends the file, 02 and 04 extend the address, 03 and 05 are start addresses.
Data · 48 B1 08 47The four payload bytes are preserved exactly; their instruction meaning depends on the target architecture.
Checksum · 00Stored value. This one is wrong: arithmetic says 14. That is the single failing record in the sample.

The record occupies absolute address 0x08008020 because a preceding :020000040800F2 line set the upper 16 bits to 0x0800. Without that line the address would only be 0x8020.

Motorola S-record

S7 termination · byte by byte

Type · S7Terminates an S3 stream and carries a 32-bit execution address.
Count · 05Five bytes follow: four address bytes plus one checksum byte.
Address · 00 00 00 00The execution address is 0x00000000; this is metadata, not a data write.
Data · noneS7 has no payload; S1, S2 and S3 carry data with 16-, 24- and 32-bit addresses.
Checksum · FAThe one's complement of count plus address bytes closes this record.

Hover or focus any byte for its role. The exact input is S70500000000FA.

02 · How the checksum is computed

Intel HEX uses a two's complement checksum. Add every byte after the colon except the checksum itself, keep the low byte, then complement and add one. The result must equal the stored byte.

S-record · one's complement

Binlet recomputes this for every line on every load. A failing checksum does not hide the data: the record stays in the table so you can decide whether to repair the byte or reject the file.

03 · Gaps are not bytes

A missing range in the record stream is not the same as a range filled with 0xFF. One is an absence of information; the other is an explicit claim about the device.

Gap

No record covers the range. The map draws it as an empty striped band, and the tool refuses to pretend it knows what the flash holds there. In the sample, 32,736 bytes sit between the bootloader and the application.

Explicit 0xFF

A record actually contains 0xFF bytes. The sample has 16 such bytes at 0x08009FF0. They can be verified, edited, and compared, because they exist in the file.

An erase operation turns covered bytes into explicit 0xFF records. A fill operation can also materialise a gap. Both are writes, and both go through the same conflict gate as any other staged change.

05 · Why a BIN needs a base

A raw binary has no idea where it belongs in memory. Binlet does not guess quietly: it asks for a base and marks every address downstream of that choice.

With base 0x08000000, the APP writes at 0x08008000. With base 0x00000000, the same bytes write to 0x00008000.

The bytes never move; the interpretation does. That is why the assumed base is shown on every screen and why changing it re-draws the whole map instead of silently relabelling a few rows.

See the BIN state

The sample is Intel HEX, so no base is invented. The BIN state exists to make the assumption visible: it is a working choice, not a property of the file.

06 · Before you write

Reading is cheap; writing is not. These are the checks Binlet keeps in front of you, in the order they matter.

Every record verifies, or you know why notThe sample has seven verified records and one failure with its arithmetic shown. A failing record is never silently repaired.
You know which addresses are recordedIntel HEX and S-record supply addresses. A BIN base is an assumption and stays labelled as one.
Every overlap has an orderStaged operations that claim the same bytes produce a conflict. Choosing a resolution records which intent wins; it never hides the overlap.
Nothing is written until you applyOperations change a working copy in this browser. The source file on disk stays untouched, and the gate stays closed while a conflict is open.
